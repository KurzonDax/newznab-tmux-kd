# Release imagery stores a viewport-capped full-size copy beside the thumb, and oversized sources are downscaled instead of rejected

Extracted Sample Images and Generated Previews were stored as a single tiny display copy (650×650 / 800×600 boxes, WebP q82) and the source bytes were discarded — the only surviving rendering was too small to be useful, and any source over 20 MB or 40 MP was rejected outright, so those releases never got imagery at all. Prod held 2,774 sample thumbs averaging ~39 KB and 70,167 preview thumbs averaging ~12.5 KB on a 3.6 TB volume with 3.3 TB free: the small sizes were protecting disk that needed no protecting.

We decided each new release's sample and preview imagery is stored as **two files**: the display thumb exactly as before, plus a **Full-size copy** — downscaled only as needed to fit a 1920×1920 box (aspect-preserved, never upscaled) and re-encoded WebP at quality 90 (both configurable). The old 20 MB / 40 MP limits stop being rejection lines: dimensions are sniffed from the file header without decoding, anything at or under a hard ceiling (default 100 MB / 120 MP, configurable) is decoded and downscaled, anything over is refused and logged. This applies only to files extracted from releases; remote metadata artwork (posters, banners, backdrops, covers) keeps its existing limits and sizes untouched. The web image modal offers a Fullscreen view of the Full-size copy only when one exists on disk.

Deliberate choices a future reader may be tempted to "fix":

- **Always re-encode; never store or serve the poster's bytes verbatim.** The full decode + fresh encode is the sanitization step — it is what guarantees a "sample.jpg" pulled out of an arbitrary Usenet post cannot carry a payload into the covers directory the web server serves. Storing originals losslessly was considered and rejected for exactly this reason; "keep every pixel" is not worth "serve attacker-controlled bytes".
- **1920, not original resolution.** The maintainer's judgment: very few visitors browse at full 1440p/4K, the Fullscreen view fits the image inside the viewport anyway, and WebP cannot encode a side over 16,383 px, so "no cap" would need a format fallback for rare monsters. The cap is a config default, not a constant.
- **A hard ceiling still exists.** Resizing requires decoding (~4–8 bytes per pixel in RAM with Imagick), and a kilobyte-sized file can claim gigapixel dimensions — the classic decompression bomb. The header check before decode is the bomb defense; removing the ceiling entirely re-opens it.
- **New releases only, permanently.** The back catalog keeps its thumbs; regeneration would mean re-downloading sample articles per release, and the maintainer explicitly decided it will not be done — this is not a deferred decision awaiting tooling. The Fullscreen control hides itself where no Full-size copy exists, so the catalog split is invisible in the UI.
