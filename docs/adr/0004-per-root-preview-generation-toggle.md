# Preview generation is toggleable per root category, with skip state and owed regeneration

Generating a release's preview image and sample video costs ffmpeg CPU, preview disk, and the bandwidth of downloading sample articles whose only purpose is to feed ffmpeg. Until now this work was category-blind: once a release entered additional post-processing, previews were attempted regardless of what the release was. Operators need to turn that work off for whole root categories (e.g. XXX) without touching the rest of the pipeline.

We decided on a per-root toggle, `root_categories.generate_previews` (default on for every root), AND-ed with the site-wide `processthumbnails`/`processvideos` switches — the root toggle can only disable, never enable. It governs the two ffmpeg-generated artifacts (Generated Preview, Generated Sample Video) and the sample-article downloads dedicated to them, and nothing else: password inspection, archive inspection, and Extracted Sample Images proceed unchanged. A release skipped by the toggle records `haspreview = -2` ("skipped by category policy"), a fourth state alongside `-1` pending / `0` attempted-none / `1` exists.

Deliberate choices a future reader may be tempted to "fix":

- **The `-2` sentinel is load-bearing, not redundant with `0`.** It is what distinguishes "never tried because policy" from "tried, produced nothing" — only the former is owed generation when a release is recategorized into a root with generation enabled. Collapsing it into `0` silently breaks owed regeneration. Display surfaces check `== 1` and the candidate query selects `-1`, so `-2` is invisible to both by construction; Manticore stores `haspreview` signed for exactly this family of sentinels.
- **Regeneration on recategorization, but not on toggle re-enable.** Moving a skipped release into an enabled root flips it back to pending, and the normal additional-processing cycle regenerates (a full pipeline re-run — there is no preview-only fast path, by choice). Re-enabling a root's toggle owes nothing automatically; the explicit backfill tool is `releases:requeue-missing-video-previews`, which selects `haspreview IN (0, -2)` restricted to enabled roots. A sweep-based trigger was rejected precisely because it cannot tell these two situations apart.
- **The owed-preview check is a hook called at each category-write site, not an observer.** Every post-creation `categories_id` write in this codebase is a query-builder update, so `ReleaseObserver` never fires for category changes — the same reason each write site already hand-calls search-index sync. The hook follows that established convention. A new write site must call it (as it must call search sync); a central recategorization funnel would subsume both if ever built.
- **The legacy `disablepreview` columns are gone, replaced, not extended.** `root_categories.disablepreview` had no runtime reader; `categories.disablepreview` had one reader that excluded matching categories from additional processing *entirely* (far broader than a preview toggle) but had been unreachable from the admin UI, which hard-coded it off on every save. Reviving either would have shipped misleading semantics under a familiar name.

Per-root toggles settled in a grilling session on 2026-08-14. See `CONTEXT.md` for **Generated Preview**, **Generated Sample Video**, **Extracted Sample Image**, and **Preview Generation** vocabulary.
